# Scout on k3s — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move production Scout off a laptop onto a Hetzner box running k3s, without losing the purchase history and without a rolling update colliding with itself.

**Architecture:** One CX32 running k3s. Traefik (bundled) as the shared ingress, cert-manager for TLS, Scout as a single-replica Deployment with `Recreate`, a local-path PVC for the database, and a Secret built from `.env`. The image is built on the box and imported into containerd, tagged with the git SHA.

**Tech Stack:** k3s, Traefik, cert-manager, kubectl. No Terraform, no registry, no Helm beyond cert-manager's install manifest.

---

## Tasks 1–3 need no server

They are the image change, the manifests, and the deploy script — all reviewable
against the repo before anything is provisioned. Tasks 4–8 need the box to
exist and its IP to be known.

## Verified before writing this plan

Measured against `87a0393`, not assumed:

| Claim | How it was checked | Result |
|---|---|---|
| The image has no init and no entrypoint | read `Dockerfile:36-41` | `USER scout`, `CMD ["scout-telegram"]`, PID 1 with nothing reaping |
| Compose relies on `init: true` | `compose.yaml:9-13` | comment records 35 zombies from one render |
| Chromium needs no extra privileges | `tools/browser.rs` flags | already passes `--no-sandbox` and `--disable-dev-shm-usage` |
| The drain window | `compose.yaml:17-20` | `stop_grace_period: 330s`, bounded by RUN_BUDGET |
| Secrets to carry across | `grep -oE '^[A-Z_]+=' .env` | 12 keys |
| The web server's port | `main.rs`, `SCOUT_WEB_BIND` | defaults to `0.0.0.0:8080` |
| The health route | `crates/scout-web/src/lib.rs` | `/healthz`, liveness only, never touches the database |

**Two landmines that turned out to be pre-solved**, recorded so nobody
"fixes" them by adding privileges: Chromium already runs with `--no-sandbox`,
so the pod needs no `SYS_ADMIN` capability; and `--disable-dev-shm-usage` means
the 64 MB default `/dev/shm` is not a problem, so no memory-backed emptyDir is
needed.

## File Structure

```
scout/
  Dockerfile                    gains tini as ENTRYPOINT
  deploy/k8s/
    namespace.yaml
    pvc.yaml
    deployment.yaml             replicas 1, Recreate, 330s grace
    service.yaml
    ingress.yaml                traefik + cert-manager annotation
    issuer.yaml                 ClusterIssuer, Let's Encrypt HTTP-01
  scripts/deploy-k3s.sh         build, import, apply, wait
```

`deploy/k8s/` holds no secrets. The Secret is created imperatively from `.env`
and never enters git.

### Task 1: The image reaps its children

**Files:**
- Modify: `Dockerfile`

Kubernetes has no `init: true`. Putting the init in the image fixes compose and
the cluster at once, and means the orchestrator cannot forget.

- [ ] **Step 1: Add tini to the runtime stage**

In the `apt-get install` list of the runtime stage (`Dockerfile:29-32`), add
`tini`, and after `USER scout` add:

```dockerfile
# Chromium's helper processes (renderer, zygote, crashpad) outlive the process
# that spawned them and are reparented to PID 1. Without an init there they are
# never reaped: one render left 35 zombies, which ends in an exhausted PID
# table. Compose can supply one with `init: true`; Kubernetes cannot, so it
# belongs in the image, where every runtime gets it.
ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["scout-telegram"]
```

Replace the existing bare `CMD`, do not add a second one.

- [ ] **Step 2: Build and prove it reaps**

```bash
docker compose build
docker compose run --rm --entrypoint sh scout -c 'ps -o pid,comm | head -3'
```

Expected: PID 1 is `tini`, not `sh`. That is the whole property — if PID 1 is
anything else, the zombies come back.

- [ ] **Step 3: Confirm the bot still starts**

```bash
docker compose up -d && sleep 20
docker compose logs --tail 5 | grep -E "scout is up|front door"
docker compose down
```

Expected: both lines. `tini --` must pass through both the command and the
signals; a bot that starts but ignores SIGTERM would fail Task 8's drain.

- [ ] **Step 4: Commit**

```bash
git add Dockerfile
git commit -m "build: the image reaps its own zombies"
```

### Task 2: The manifests

**Files:**
- Create: `deploy/k8s/{namespace,pvc,deployment,service,ingress,issuer}.yaml`

- [ ] **Step 1: Namespace and storage**

`deploy/k8s/namespace.yaml`:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: scout
```

`deploy/k8s/pvc.yaml`:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: scout-data
  namespace: scout
spec:
  accessModes: [ReadWriteOnce]
  # k3s's bundled provisioner. A directory on this node's disk, which is
  # honest about what it is: there is one node, so there is no network
  # volume to be had, and the backup story is Hetzner's snapshots plus the
  # dump in Task 7 rather than a storage layer.
  storageClassName: local-path
  resources:
    requests:
      storage: 5Gi
```

The live database is about 15 MB; 5 Gi is room for years of it plus the
`.pre-*` backups taken before each migration.

- [ ] **Step 2: The Deployment**

`deploy/k8s/deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: scout
  namespace: scout
spec:
  # Not a knob. DuckDB is single-writer, so a second process cannot open the
  # database — and two clients long-polling one Telegram bot token both get
  # 409 Conflict. Scaling this up breaks the bot in two ways at once, and
  # neither failure names the replica count.
  replicas: 1
  strategy:
    # For the same reason: the default rolling update starts the new pod
    # before stopping the old one, which is exactly the collision above,
    # on every single deploy.
    type: Recreate
  selector:
    matchLabels: { app: scout }
  template:
    metadata:
      labels: { app: scout }
    spec:
      # One request is bounded by RUN_BUDGET (300s) plus link verification
      # and wrap-up. Anything less and a deploy kills the slowest answers
      # mid-sentence. Reached only when something is running; an idle bot
      # exits at once.
      terminationGracePeriodSeconds: 330
      containers:
        - name: scout
          # The deploy script replaces this with the git SHA it just built.
          # IfNotPresent rather than Never: there is no registry, so a
          # missing image should fail loudly rather than silently run
          # whatever `latest` happens to be.
          image: scout:latest
          imagePullPolicy: IfNotPresent
          envFrom:
            - secretRef:
                name: scout
          env:
            - { name: SCOUT_DB_PATH, value: /data/scout.duckdb }
            - { name: SCOUT_WEB_BIND, value: "0.0.0.0:8080" }
          ports:
            - { name: http, containerPort: 8080 }
          # /healthz reports process liveness and deliberately says nothing
          # about the database — a check that failed while DuckDB was busy
          # would restart a pod that was serving correctly from cache.
          readinessProbe:
            httpGet: { path: /healthz, port: http }
            initialDelaySeconds: 5
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /healthz, port: http }
            initialDelaySeconds: 30
            periodSeconds: 20
            failureThreshold: 3
          resources:
            requests: { cpu: 200m, memory: 512Mi }
            # Memory only. A CPU limit would throttle the agent mid-answer
            # for no benefit on a box running one workload.
            limits: { memory: 3Gi }
          securityContext:
            # The image already runs as `scout`, and Chromium is invoked
            # with --no-sandbox, so nothing here needs privileges.
            allowPrivilegeEscalation: false
            capabilities: { drop: [ALL] }
          volumeMounts:
            - { name: data, mountPath: /data }
      volumes:
        - name: data
          persistentVolumeClaim: { claimName: scout-data }
```

- [ ] **Step 3: Service and Ingress**

`deploy/k8s/service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: scout
  namespace: scout
spec:
  selector: { app: scout }
  ports:
    - { name: http, port: 80, targetPort: http }
```

`deploy/k8s/ingress.yaml` — `SCOUT_DOMAIN` is substituted by the deploy script,
because a hostname cannot be templated by `kubectl` alone:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: scout
  namespace: scout
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
spec:
  ingressClassName: traefik
  tls:
    - hosts: ["${SCOUT_DOMAIN}"]
      secretName: scout-tls
  rules:
    - host: "${SCOUT_DOMAIN}"
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: scout
                port: { name: http }
```

- [ ] **Step 4: The issuer**

`deploy/k8s/issuer.yaml` — `SCOUT_ACME_EMAIL` is likewise substituted:

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: "${SCOUT_ACME_EMAIL}"
    privateKeySecretRef:
      name: letsencrypt-account-key
    solvers:
      - http01:
          ingress:
            ingressClassName: traefik
```

Add `SCOUT_ACME_EMAIL=you@example.com` to `.env.example`. **Do not edit `.env`**
— the human running the deploy sets it, and Task 5 fails loudly if they have
not.

- [ ] **Step 5: Check they parse**

Without a cluster, `kubectl` can still validate structure:

```bash

    kubectl apply --dry-run=client -f - >/dev/null && echo "ok  $f" || echo "BAD $f"
done
```

Expected: `ok` for all but `issuer.yaml`, which needs cert-manager's CRDs to be

### Task 3: The deploy script

**Files:**
- Create: `scripts/deploy-k3s.sh`

`scripts/deploy.sh` stays as it is — it is how Scout runs locally, and it works.

- [ ] **Step 1: Write it**

```bash
#!/usr/bin/env bash
# Deploy scout to the k3s node.
#
# Runs ON the node: it builds with docker, imports into k3s's containerd, and
# applies. There is no registry, which is the right trade for one machine —
# and it means the image only ever exists where it is used.
set -euo pipefail
cd "$(dirname "$0")/.."

DRY_RUN=0
[ "${1:-}" = "--dry-run" ] && DRY_RUN=1

say() { printf '\n\033[1m==> %s\033[0m\n' "$1"; }

: "${SCOUT_DOMAIN:?set SCOUT_DOMAIN (it is in .env)}"
: "${SCOUT_ACME_EMAIL:?set SCOUT_ACME_EMAIL (it is in .env)}"

# A deploy is identified by what is in git, so a rollback is a tag that still
# exists in containerd rather than a rebuild that might not reproduce.
SHA=$(git rev-parse --short HEAD)
if [ -n "$(git status --porcelain -- crates Cargo.toml Cargo.lock Dockerfile deploy)" ]; then
    echo "  refusing: uncommitted changes would deploy as $SHA and not be $SHA" >&2
    git status --short -- crates Cargo.toml Cargo.lock Dockerfile deploy >&2
    exit 1
fi

say "Building scout:$SHA"
if [ "$DRY_RUN" -eq 1 ]; then echo "  (dry run)"; else
    docker build -t "scout:$SHA" .
    docker save "scout:$SHA" | sudo k3s ctr images import -
fi

say "Applying"
if [ "$DRY_RUN" -eq 1 ]; then echo "  (dry run)"; else
    kubectl apply -f deploy/k8s/namespace.yaml
    # The secret is rebuilt from .env every deploy, so rotating a key is
    # editing .env and deploying. --dry-run=client | apply is the documented
    # way to make `create secret` idempotent.
    kubectl -n scout create secret generic scout \
        --from-env-file=.env --dry-run=client -o yaml | kubectl apply -f -
    for f in pvc service deployment ingress issuer; do
        envsubst < "deploy/k8s/$f.yaml" | kubectl apply -f -
    done
    kubectl -n scout set image deployment/scout "scout=scout:$SHA"
fi

say "Waiting for the rollout"
if [ "$DRY_RUN" -eq 1 ]; then echo "  (dry run)"; else
    # Recreate means the old pod goes first, so this window includes the
    # drain: up to 330s if a request was in flight.
    if ! kubectl -n scout rollout status deployment/scout --timeout=420s; then
        echo "  the rollout did not complete" >&2
        kubectl -n scout get pods
        kubectl -n scout logs -l app=scout --tail=40
        exit 1
    fi
fi

say "Deployed: $SHA $(git log --oneline -1 --format=%s)"
```

`chmod +x scripts/deploy-k3s.sh`.

- [ ] **Step 2: Check it refuses a dirty tree**

```bash

SCOUT_DOMAIN=x SCOUT_ACME_EMAIL=y ./scripts/deploy-k3s.sh --dry-run; echo "exit=$?"

```

- [ ] **Step 3: Check the dry run passes on a clean tree**



**A human creates the server.** These steps assume it exists, its IP is known,

- [ ] **Step 1: Confirm what you are on**

```bash
ssh root@<IP> 'lsb_release -d; nproc; free -g | head -2; df -h / | tail -1'
```

- [ ] **Step 2: Close everything except what is needed**

In the Hetzner Cloud console, attach a firewall to the server allowing inbound

This is not optional. **k3s serves its API on 6443 bound to all interfaces**,
so an unfirewalled box publishes cluster administration to the internet.
Verify from somewhere else afterwards:

```bash
nc -zv -w 5 <IP> 6443   # must fail
nc -zv -w 5 <IP> 443    # must succeed once Task 6 is done
```

- [ ] **Step 3: Install k3s and docker**

```bash
ssh root@<IP> 'curl -sfL https://get.k3s.io | sh -'
ssh root@<IP> 'curl -fsSL https://get.docker.com | sh'
# envsubst substitutes the domain into the ingress; it is not always present

ssh root@<IP> 'apt-get update && apt-get install -y gettext-base git'
ssh root@<IP> 'k3s kubectl get nodes'
```

Expected: one node, `Ready`, roles `control-plane,master`. k3s does not taint
it, so workloads schedule there with nothing further to do.

Docker is installed alongside k3s purely to build images; k3s uses its own
containerd and does not go through it.

### Task 5: cert-manager *(needs the box)*

- [ ] **Step 1: Install it**

```bash
ssh root@<IP> 'k3s kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml'
```

The webhook is the one to wait for: applying a `ClusterIssuer` before it is

- [ ] **Step 2: Check DNS before anything asks Let's Encrypt for a certificate**

```bash
dig +short $SCOUT_DOMAIN A
```

Expected: the server's IP, and **nothing else**. If it is empty, or points at
Cloudflare's proxy, stop. An HTTP-01 challenge that cannot reach Traefik fails,
retries, and consumes a rate limit measured in hours.

In Cloudflare the record must be **DNS only (grey cloud)** for the first
issuance. It can be proxied afterwards.

```bash
ssh root@<IP> 'git clone https://github.com/watchcat/scout.git /opt/scout'
```

```bash
ssh root@<IP> 'k3s kubectl -n scout scale deploy/scout --replicas=0'
```

### Task 7: Move the database *(needs the box)*

The unforgiving part. Read all of it before starting.

- [ ] **Step 1: Stop the laptop's bot**

```bash
docker compose down
```

From here until Step 5 there is no bot. That is expected and it is why this is
one task rather than five.

- [ ] **Step 2: Copy the database out without starting the bot again**

```bash
docker compose run --rm --entrypoint sh scout \
  -c 'cat /data/scout.duckdb' > /tmp/scout.duckdb
ls -l /tmp/scout.duckdb
```

`run --entrypoint sh` mounts the same volume and runs a shell instead of the
bot, so nothing connects to Telegram. **Never copy the file from the host** —
the host's DuckDB is older than the one that wrote it and must not open it.

Record the size. It should be roughly 15 MB.

- [ ] **Step 3: Put it on the node's volume**

**Nothing may be writing the file while it is replaced.** The Deployment is
already at zero replicas from Task 6, and it stays there for this whole step —
copying over a database a running pod has open is how you get a corrupted one.

`local-path` is a directory on the node, so with no pod running the file can
simply be placed there. That avoids `kubectl cp` entirely, which is worth
avoiding: it needs `tar` inside the container and it needs a pod to exist.

```bash
scp /tmp/scout.duckdb root@<IP>:/tmp/scout.duckdb

# Confirm nothing is running before touching the volume.
ssh root@<IP> 'k3s kubectl -n scout get pods'          # expect: No resources found

# Find the directory the PVC is bound to.
ssh root@<IP> 'k3s kubectl -n scout get pv -o jsonpath="{.items[?(@.spec.claimRef.name==\"scout-data\")].spec.hostPath.path}"; echo'
```

Take that path — it looks like
`/var/lib/rancher/k3s/storage/pvc-<uuid>_scout_scout-data` — and place the
file, owned by the user the container runs as:

```bash
UID_GID=$(ssh root@<IP> 'docker run --rm scout:$(cd /opt/scout && git rev-parse --short HEAD) id -u -n; echo')
ssh root@<IP> 'id -u scout 2>/dev/null || echo "(the container user, not a host user)"'

ssh root@<IP> 'cp /tmp/scout.duckdb <PVC_PATH>/scout.duckdb'
ssh root@<IP> 'chown 1000:1000 <PVC_PATH>/scout.duckdb && ls -l <PVC_PATH>/'
```

**Check the UID rather than trusting 1000.** The image does `useradd -m scout`
on debian-slim, which yields 1000 on a fresh image, but a wrong owner here
produces a permission error at start-up that reads like a corrupt database.
Confirm with `docker run --rm scout:<sha> id -u`.

Then start it:

```bash
ssh root@<IP> 'k3s kubectl -n scout scale deploy/scout --replicas=1'
ssh root@<IP> 'k3s kubectl -n scout rollout status deploy/scout --timeout=300s'
```

The pod opens the file that was put there. Scout's migration runner sees a
database already at the current schema version and does nothing, which is the
same thing it does on every ordinary restart.

- [ ] **Step 4: Prove nothing was lost**

```bash
ssh root@<IP> "k3s kubectl -n scout logs -l app=scout --tail=20 | grep 'who may talk'"
```

Expected: the same `founders=`, `members=` and `schema=` values the laptop
reported. `schema=5` in particular — a lower number means the fresh database is
still in place and the copy did not take.

Then in the chat: an ordinary question, `/stat`, and `/invite status`. `/stat`
is the one that reads history, so it is the one that proves the file arrived.

- [ ] **Step 5: Keep the laptop's copy**

Do not delete the local volume. It is the rollback.

## What this plan deliberately does not do

- **No second service.** The ingress and cert-manager are shared by design, but
  nothing else is deployed here.
- **No off-box backups.** Hetzner's snapshots cover disk failure. They do not
  cover deleting the wrong namespace, and a periodic dump to somewhere else is
  wanted and not in scope.
- **No monitoring.** `kubectl` is the whole story. The first thing that will
  hurt is not noticing a certificate that failed to renew.
- **No GitOps.** Manifests are applied by a script from a checkout. Right for
  one service, wrong for ten.
- **`compose.yaml` and `Caddyfile` are not deleted.** Compose is still how
  Scout runs locally. The Caddyfile is superseded but harmless, and deleting it
  in the same change that moves hosts would confuse a rollback.
