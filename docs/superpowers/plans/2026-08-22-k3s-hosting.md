# Scout on k3s — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move production Scout off a laptop onto a Contabo VPS running k3s, without losing the purchase history and without a rolling update colliding with itself.

**Architecture:** One Contabo VPS running k3s, firewalled with `ufw` because the provider offers none. Traefik (bundled) as the shared ingress, cert-manager for TLS, Scout as a single-replica Deployment with `Recreate`, a local-path PVC for the database, and a Secret piped in from `.env`. The image is built on the developer's machine and shipped over SSH into containerd, tagged with the git SHA.

**Tech Stack:** k3s, Traefik, cert-manager, kubectl. No Terraform, no registry, no Helm beyond cert-manager's install manifest.

---

## Tasks 1–3 need no server

They are the image change, the manifests, and the deploy script — all reviewable
against the repo before anything is provisioned. Tasks 4–8 need the box to
exist and its IP to be known.

## Verified before writing this plan

Measured against `87a0393`, not assumed:

| Claim | How it was checked | Result |
|---|---|---|
| The image has no init and no entrypoint | read `Dockerfile:36-41` | `USER scout`, `CMD ["scout-telegram"]`, PID 1 with nothing reaping |
| Compose relies on `init: true` | `compose.yaml:9-13` | comment records 35 zombies from one render |
| Chromium needs no extra privileges | `tools/browser.rs` flags | already passes `--no-sandbox` and `--disable-dev-shm-usage` |
| The drain window | `compose.yaml:17-20` | `stop_grace_period: 330s`, bounded by RUN_BUDGET |
| Secrets to carry across | `grep -oE '^[A-Z_]+=' .env` | 12 keys |
| The web server's port | `main.rs`, `SCOUT_WEB_BIND` | defaults to `0.0.0.0:8080` |
| The health route | `crates/scout-web/src/lib.rs` | `/healthz`, liveness only, never touches the database |

**Two landmines that turned out to be pre-solved**, recorded so nobody
"fixes" them by adding privileges: Chromium already runs with `--no-sandbox`,
so the pod needs no `SYS_ADMIN` capability; and `--disable-dev-shm-usage` means
the 64 MB default `/dev/shm` is not a problem, so no memory-backed emptyDir is
needed.

### Task 1: The image reaps its children

**Files:**
- Modify: `Dockerfile`

Kubernetes has no `init: true`. Putting the init in the image fixes compose and
the cluster at once, and means the orchestrator cannot forget.

- [ ] **Step 1: Add tini to the runtime stage**

In the `apt-get install` list of the runtime stage (`Dockerfile:29-32`), add
`tini`, and after `USER scout` add:

```dockerfile
# Chromium's helper processes (renderer, zygote, crashpad) outlive the process
# that spawned them and are reparented to PID 1. Without an init there they are
# never reaped: one render left 35 zombies, which ends in an exhausted PID
# table. Compose can supply one with `init: true`; Kubernetes cannot, so it
# belongs in the image, where every runtime gets it.
ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["scout-telegram"]
```

Replace the existing bare `CMD`, do not add a second one.

- [ ] **Step 2: Build and prove it reaps**

```bash
docker compose build
docker run --rm scout-scout:latest sh -c 'ps -o pid,comm | head -4'
```

Expected: PID 1 is `tini`, with `sh` as its child. That is the whole property —
if PID 1 is anything else, the zombies come back.

Replace the **command**, not the entrypoint. `--entrypoint sh` removes tini
from the chain, which is the thing being tested — and under `docker compose
run` it reports PID 1 as `docker-init`, because compose's own `init: true`
supplies one. Both readings look plausible and neither tells you whether the
image has an init of its own.

- [ ] **Step 3: Confirm the binary still launches — without touching production**

**Do not run `docker compose up`.** Production Scout is this compose project on
this machine until Task 8 moves it. `up -d` would deploy an unreviewed image to
the live bot, and `down` would then leave it stopped.

Run the image with no environment instead. It gets as far as reading config,
fails on the first missing variable, and exits — which proves the entrypoint
chain reaches the binary, without a second client touching Telegram (two on one
token get 409 and neither works):

```bash
docker run --rm scout-scout:latest 2>&1 | head -3; echo "exit=${PIPESTATUS[0]}"
```

Expected: `missing required env var TELEGRAM_BOT_TOKEN` and a non-zero exit.
A "no such file or directory" or an exec-format error means `tini` did not
hand off to the command.

Signal forwarding is tini's whole purpose and is not re-tested here; what Task 8
verifies is the drain, against the real thing.

- [ ] **Step 4: Commit**

```bash
git add Dockerfile
git commit -m "build: the image reaps its own zombies"
```

### Task 2: The manifests

**Files:**
- Create: `deploy/k8s/{namespace,pvc,deployment,service,ingress,issuer}.yaml`

- [ ] **Step 1: Namespace and storage**

`deploy/k8s/namespace.yaml`:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: scout
```

`deploy/k8s/pvc.yaml`:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: scout-data
  namespace: scout
spec:
  accessModes: [ReadWriteOnce]
  # k3s's bundled provisioner. A directory on this node's disk, which is
  # honest about what it is: there is one node, so there is no network
  # volume to be had. On this provider there are no free snapshots either,
  # so the dump in Task 7 is the whole backup story until someone buys the
  # Auto Backup add-on.
  storageClassName: local-path
  resources:
    requests:
      storage: 5Gi
```

The live database is about 15 MB; 5 Gi is room for years of it plus the
`.pre-*` backups taken before each migration.

- [ ] **Step 2: The Deployment**

`deploy/k8s/deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: scout
  namespace: scout
spec:
  # Not a knob. DuckDB is single-writer, so a second process cannot open the
  # database — and two clients long-polling one Telegram bot token both get
  # 409 Conflict. Scaling this up breaks the bot in two ways at once, and
  # neither failure names the replica count.
  replicas: 1
  strategy:
    # For the same reason: the default rolling update starts the new pod
    # before stopping the old one, which is exactly the collision above,
    # on every single deploy.
    type: Recreate
  selector:
    matchLabels: { app: scout }
  template:
    metadata:
      labels: { app: scout }
    spec:
      # One request is bounded by RUN_BUDGET (300s) plus link verification
      # and wrap-up. Anything less and a deploy kills the slowest answers
      # mid-sentence. Reached only when something is running; an idle bot
      # exits at once.
      terminationGracePeriodSeconds: 330
      containers:
        - name: scout
          # The deploy script replaces this with the git SHA it just built.
          # IfNotPresent rather than Never: there is no registry, so a
          # missing image should fail loudly rather than silently run
          # whatever `latest` happens to be.
          image: scout:latest
          imagePullPolicy: IfNotPresent
          envFrom:
            - secretRef:
                name: scout
          env:
            - { name: SCOUT_DB_PATH, value: /data/scout.duckdb }
            - { name: SCOUT_WEB_BIND, value: "0.0.0.0:8080" }
          ports:
            - { name: http, containerPort: 8080 }
          # /healthz reports process liveness and deliberately says nothing
          # about the database — a check that failed while DuckDB was busy
          # would restart a pod that was serving correctly from cache.
          readinessProbe:
            httpGet: { path: /healthz, port: http }
            initialDelaySeconds: 5
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /healthz, port: http }
            initialDelaySeconds: 30
            periodSeconds: 20
            failureThreshold: 3
          resources:
            requests: { cpu: 200m, memory: 512Mi }
            # Memory only. A CPU limit would throttle the agent mid-answer
            # for no benefit on a box running one workload.
            limits: { memory: 3Gi }
          securityContext:
            # The image already runs as `scout`, and Chromium is invoked
            # with --no-sandbox, so nothing here needs privileges.
            allowPrivilegeEscalation: false
            capabilities: { drop: [ALL] }
          volumeMounts:
            - { name: data, mountPath: /data }
      volumes:
        - name: data
          persistentVolumeClaim: { claimName: scout-data }
```

`deploy/k8s/ingress.yaml` — `SCOUT_DOMAIN` is substituted by the deploy script,

```yaml
metadata:
  name: scout
  namespace: scout
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
spec:
  ingressClassName: traefik
  tls:
    - hosts: ["${SCOUT_DOMAIN}"]
      secretName: scout-tls
  rules:
    - host: "${SCOUT_DOMAIN}"
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: scout
                port: { name: http }
```

- [ ] **Step 4: The issuer**

`deploy/k8s/issuer.yaml` — `SCOUT_ACME_EMAIL` is likewise substituted:

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: "${SCOUT_ACME_EMAIL}"
    privateKeySecretRef:
      name: letsencrypt-account-key
    solvers:
      - http01:
          ingress:
            ingressClassName: traefik
```

Add `SCOUT_ACME_EMAIL=you@example.com` to `.env.example`. **Do not edit `.env`**
— the human running the deploy sets it, and Task 5 fails loudly if they have
not.

- [ ] **Step 5: Check they parse**

**`kubectl` cannot validate these offline.** `--dry-run=client` still fetches
the API group list to resolve a kind, and `--validate=false` only skips the
schema check, not that lookup — both fail with a connection refused against
`localhost:8080`. Anything claiming otherwise has a cluster configured.

What is checkable without one: the YAML parses, and every `${...}` was
substituted. The second matters more than it sounds — an unsubstituted host
produces an Ingress that serves a literal `${SCOUT_DOMAIN}`, which fails as a
404 from Traefik rather than as an error from `kubectl`.

```bash
for f in deploy/k8s/*.yaml; do
  out=$(SCOUT_DOMAIN=example.com SCOUT_ACME_EMAIL=a@example.com envsubst < "$f")
  echo "$out" | python3 -c 'import sys,yaml; yaml.safe_load(sys.stdin)' || { echo "BAD yaml $f"; continue; }
  echo "$out" | grep -q '\${' && echo "UNSUBSTITUTED $f" || echo "ok  $(basename $f)"
done
```

Expected: `ok` for all six. Real validation happens at Task 6's first apply,
against the cluster, which is the only place it can.


### Task 3: The deploy script

**Files:**
- Create: `scripts/deploy-k3s.sh`

`scripts/deploy.sh` stays as it is — it is how Scout runs locally, and it works.

- [ ] **Step 1: Write it**

```bash
#!/usr/bin/env bash
# Deploy scout to the k3s node.
#
# Runs HERE, not on the node. The image is built locally and shipped over SSH
# into k3s's containerd; the manifests are piped through SSH to kubectl. The
# server therefore needs no Docker, no build toolchain, and no copy of this
# repository — it runs k3s and Scout and nothing else, which is both cheaper
# and less to attack.
#
# The other half of that trade: a deploy needs a machine with Docker, and the
# first image push is a slow upload.
#
#   scripts/deploy-k3s.sh            build, ship, apply, wait
#   scripts/deploy-k3s.sh --dry-run  print the plan, change nothing
set -euo pipefail
cd "$(dirname "$0")/.."

DRY_RUN=0
[ "${1:-}" = "--dry-run" ] && DRY_RUN=1

say() { printf '\n\033[1m==> %s\033[0m\n' "$1"; }
step() { if [ "$DRY_RUN" -eq 1 ]; then echo "  (dry run) $1"; return 1; fi; return 0; }

: "${SCOUT_DOMAIN:?set SCOUT_DOMAIN — it is in .env}"
: "${SCOUT_ACME_EMAIL:?set SCOUT_ACME_EMAIL — it is in .env}"
: "${SCOUT_SSH:?set SCOUT_SSH to the node, e.g. root@203.0.113.4}"

SSH=(ssh -o BatchMode=yes "$SCOUT_SSH")

# A deploy is named by what is in git, so a rollback is a tag that still exists
# in containerd rather than a rebuild that might not reproduce.
SHA=$(git rev-parse --short HEAD)
if [ -n "$(git status --porcelain -- crates Cargo.toml Cargo.lock Dockerfile deploy scripts)" ]; then
    echo "  refusing: uncommitted changes would ship as $SHA without being $SHA" >&2
    git status --short -- crates Cargo.toml Cargo.lock Dockerfile deploy scripts >&2
    exit 1
fi

say "Building scout:$SHA here"
step "docker build -t scout:$SHA ." && docker build -t "scout:$SHA" .

say "Shipping it to $SCOUT_SSH"
# gzip -1 rather than the default: the layers that matter are already
# compressed, so the cheap setting gets most of the saving for a fraction of
# the CPU. Expect minutes on the first push and seconds afterwards, since only
# the top layer changes.
step "docker save | gzip | ssh | k3s ctr images import" \
    && docker save "scout:$SHA" | gzip -1 | "${SSH[@]}" 'gunzip | k3s ctr images import -'

say "Applying"
step "kubectl apply namespace" \
    && "${SSH[@]}" 'kubectl apply -f -' < deploy/k8s/namespace.yaml
# .env never lands on the node: it is piped in, used, and gone. The values do
# end up in the cluster's datastore, which is the same trust boundary they
# already have on this machine.
step "kubectl create secret from .env (piped, not copied)" \
    && "${SSH[@]}" 'kubectl -n scout create secret generic scout \
         --from-env-file=/dev/stdin --dry-run=client -o yaml | kubectl apply -f -' < .env
for f in pvc service deployment ingress issuer; do
    step "apply deploy/k8s/$f.yaml" \
        && envsubst < "deploy/k8s/$f.yaml" | "${SSH[@]}" 'kubectl apply -f -'
done
step "set image scout:$SHA" \
    && "${SSH[@]}" "kubectl -n scout set image deployment/scout scout=scout:$SHA"

say "Waiting for the rollout"
# Recreate stops the old pod before starting the new one, so this window
# includes the drain: up to 330s when a request was in flight.
if step "kubectl rollout status"; then
    if ! "${SSH[@]}" 'kubectl -n scout rollout status deployment/scout --timeout=420s'; then
        echo >&2
        echo "  the rollout did not complete" >&2
        "${SSH[@]}" 'kubectl -n scout get pods; kubectl -n scout logs -l app=scout --tail=40' >&2
        exit 1
    fi
fi

say "Deployed: $SHA $(git log --oneline -1 --format=%s)"
```

`chmod +x scripts/deploy-k3s.sh`.

### Task 4: The server *(needs the box)*

**Do the steps in the order given.** k3s is installed before the firewall,
because the firewall rules reference the networks k3s creates and those should
be read from the running cluster rather than assumed.

**A human creates the server.** These steps assume it exists, its IP is known,
and SSH works. Export `SCOUT_SSH=root@<IP>` — the deploy script needs it.

- [ ] **Step 1: Confirm what you are on**

```bash
ssh $SCOUT_SSH 'lsb_release -d; nproc; free -m | head -2; df -h / | tail -1'
```

Expected: Ubuntu 24.04, and at least ~2 GB usable. The image is built
elsewhere and shipped in, so this box never compiles anything — 4 GB is
comfortable and 2 GB would run it. There is no build to be killed here, which
is the whole reason the instance can be this small.

- [ ] **Step 2: Close everything except what is needed**

**Contabo has no cloud firewall.** Hetzner and Vultr both hand you a
network-level firewall to attach; Contabo does not, so this has to be done on
the host with `ufw` — and it has to be done, because **k3s serves its API on
6443 bound to all interfaces**. An unfirewalled box publishes cluster
administration to the internet.

`ufw` and k3s interact badly if you are naive about it. A plain default-deny
also drops traffic arriving on the CNI bridge, so pods lose the API server and
CoreDNS, and the symptom is a cluster that comes up and then quietly fails to
resolve anything. The pod and service networks have to be allowed explicitly:

```bash
ssh $SCOUT_SSH 'ufw default deny incoming && ufw default allow outgoing'
ssh $SCOUT_SSH 'ufw allow 22/tcp && ufw allow 80/tcp && ufw allow 443/tcp'
# k3s's own networks. Note what is NOT here: 6443. In-cluster clients reach the
# API through the service network below or over loopback, so the port never
# needs to face the internet.
ssh $SCOUT_SSH 'ufw allow from 10.42.0.0/16 to any'   # pods
ssh $SCOUT_SSH 'ufw allow from 10.43.0.0/16 to any'   # services
ssh $SCOUT_SSH 'ufw --force enable && ufw status verbose'
```

**Do this after k3s is installed, not before** — the CIDRs above are k3s's
defaults and should be confirmed against the running cluster rather than
trusted:

```bash
ssh $SCOUT_SSH 'kubectl -n kube-system get pod -o wide | head -3'   # pod IPs in 10.42.x
ssh $SCOUT_SSH 'kubectl get svc kubernetes -o jsonpath="{.spec.clusterIP}"; echo'  # 10.43.0.1
```

Then verify from somewhere that is not the box:

```bash
nc -z -w 5 <IP> 6443    # must fail — the Kubernetes API
nc -z -w 5 <IP> 10250   # must fail — the kubelet, which can exec into pods
nc -z -w 5 <IP> 22      # must succeed
```

**6443 is not the only one.** A fresh k3s also listens on 10250 on all
interfaces — that is the kubelet, and it is the port that runs commands inside
containers. Verified on the real install: `ss -tlnp` showed both bound to `*`
before the firewall went on.

And verify from inside that the cluster still works, which is the half people
skip:

```bash
ssh $SCOUT_SSH 'kubectl -n kube-system rollout status deploy/coredns --timeout=120s'
ssh $SCOUT_SSH 'kubectl run dnstest --rm -i --restart=Never --image=busybox:1.36 -- sh -c "
  nslookup kubernetes.default.svc.cluster.local
  nslookup api.telegram.org"'
```

Expected: CoreDNS ready, the cluster name resolving to the API service, and an
external name resolving too — the second proves egress survived, which the bot
needs for Telegram.

**Use the fully qualified name.** `nslookup kubernetes.default` returns
NXDOMAIN from busybox regardless of whether anything is wrong: its resolver
mishandles short names against `ndots:5`. That looks exactly like a firewall
that has broken cluster DNS, and it is not one. An NXDOMAIN means CoreDNS
answered; a timeout is what a blocked path actually looks like.

A firewall that locks out the internet and the cluster equally is not a
success — but neither is one that gets ripped out over a bad test.

- [ ] **Step 3: Install k3s**

```bash
ssh $SCOUT_SSH 'curl -sfL https://get.k3s.io | sh -'
ssh $SCOUT_SSH 'kubectl get nodes'
```

Expected: one node, `Ready`, roles `control-plane,master`. k3s does not taint
it, so workloads schedule there with nothing further to do, and it installs a
`kubectl` symlink so the plain command works as root.

**No Docker, no git, no gettext on the box.** The image is built and the
manifests are substituted on the machine running the deploy; only the finished
artefacts cross the SSH connection. That is what keeps this instance small
enough to be cheap, and it means the internet-facing host has no compiler on
it.

Nothing in this task touches the repository. Record the IP where the next tasks
can find it.

### Task 6: First deploy *(needs the box)*

- [ ] **Step 1: Nothing to put on the box**

There is no checkout to make and no `.env` to copy. The deploy script runs
here: it builds here, pipes the image over SSH, and pipes `.env` into
`kubectl create secret` without it ever touching the node's disk. The values do
land in the cluster's datastore, which is the same trust boundary they already
have on this machine — but there is no second copy of the file to forget about.

Export what the script needs:

```bash
export SCOUT_SSH=root@<IP>
set -a && . ./.env && set +a
```

- [ ] **Step 2: Deploy with the Deployment scaled to zero**

The bot must not start yet — the laptop is still polling, and two clients on
one token get 409.

```bash
./scripts/deploy-k3s.sh
ssh $SCOUT_SSH 'kubectl -n scout scale deploy/scout --replicas=0'
```

The first run uploads the whole image and will take minutes. Later ones send
only the layer that changed.

Deploying then scaling to zero, rather than the reverse, means the rollout wait
proves the image runs before anything depends on it.

- [ ] **Step 3: Watch the certificate**

```bash
ssh $SCOUT_SSH 'kubectl -n scout get certificate,order,challenge'
```

Expected: the `Certificate` reaches `READY=True` within a minute or two. If it
does not, read the `Challenge` — it says exactly what Let's Encrypt saw, and it
is almost always DNS or the orange cloud.

### Task 7: Move the database *(needs the box)*

The unforgiving part. Read all of it before starting.

- [ ] **Step 1: Stop the laptop's bot**

```bash
docker compose down
```

From here until Step 5 there is no bot. That is expected and it is why this is
one task rather than five.

- [ ] **Step 2: Copy the database out without starting the bot again**

```bash
docker compose run --rm --entrypoint sh scout \
  -c 'cat /data/scout.duckdb' > /tmp/scout.duckdb
ls -l /tmp/scout.duckdb
```

`run --entrypoint sh` mounts the same volume and runs a shell instead of the
bot, so nothing connects to Telegram. **Never copy the file from the host** —
the host's DuckDB is older than the one that wrote it and must not open it.

Record the size. It should be roughly 15 MB.

- [ ] **Step 3: Put it on the node's volume**

**Nothing may be writing the file while it is replaced.** The Deployment is
already at zero replicas from Task 6, and it stays there for this whole step —
copying over a database a running pod has open is how you get a corrupted one.

`local-path` is a directory on the node, so with no pod running the file can
simply be placed there. That avoids `kubectl cp` entirely, which is worth
avoiding: it needs `tar` inside the container and it needs a pod to exist.

```bash
scp /tmp/scout.duckdb root@<IP>:/tmp/scout.duckdb

# Confirm nothing is running before touching the volume.
ssh $SCOUT_SSH 'kubectl -n scout get pods'          # expect: No resources found

# Find the directory the PVC is bound to.
ssh $SCOUT_SSH 'kubectl -n scout get pv -o jsonpath="{.items[?(@.spec.claimRef.name==\"scout-data\")].spec.hostPath.path}"; echo'
```

Take that path — it looks like
`/var/lib/rancher/k3s/storage/pvc-<uuid>_scout_scout-data` — and place the
file, owned by the user the container runs as:

**Check the UID rather than trusting 1000.** The image does `useradd -m scout`
on debian-slim, which yields 1000 on a fresh image, but a wrong owner here
produces a permission error at start-up that reads like a corrupt database.
Ask the image — locally, since that is where Docker is:

```bash
docker run --rm scout:$(git rev-parse --short HEAD) id -u    # expect 1000
```

```bash
ssh $SCOUT_SSH 'cp /tmp/scout.duckdb <PVC_PATH>/scout.duckdb'
ssh $SCOUT_SSH 'chown 1000:1000 <PVC_PATH>/scout.duckdb && ls -l <PVC_PATH>/'
```

Then start it:

```bash
ssh $SCOUT_SSH 'kubectl -n scout scale deploy/scout --replicas=1'
ssh $SCOUT_SSH 'kubectl -n scout rollout status deploy/scout --timeout=300s'
```

The pod opens the file that was put there. Scout's migration runner sees a
database already at the current schema version and does nothing, which is the
same thing it does on every ordinary restart.

## What this plan deliberately does not do

- **No second service.** The ingress and cert-manager are shared by design, but
  nothing else is deployed here.
- **No backups at all, yet.** Contabo's Auto Backup is a paid add-on and is
  not assumed here, so after this plan the purchase history lives on exactly
  one disk. The dump in Task 7 is a procedure, not a schedule. This is the
  largest thing left undone and it should not wait long.
- **No monitoring.** `kubectl` is the whole story. The first thing that will
  hurt is not noticing a certificate that failed to renew.
- **No GitOps.** Manifests are applied by a script from a checkout. Right for
  one service, wrong for ten.
- **`compose.yaml` and `Caddyfile` are not deleted.** Compose is still how
  Scout runs locally. The Caddyfile is superseded but harmless, and deleting it
  in the same change that moves hosts would confuse a rollback.
