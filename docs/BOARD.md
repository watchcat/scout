## Backlog

### Scaling
- [ ] **Lock-wait tracing** — a span around every store call with the time spent waiting on the mutex; the numbers decide the next card
- [ ] **DB decision** — stay on DuckDB with read-only `try_clone()` connections, or move to SQLite (`rusqlite` bundled, WAL) — SQLite also removes the 10-minute C++ build that shapes the whole deploy pipeline
- [ ] **Metrics** — a `/metrics` endpoint: runs, run duration, tool calls, provider errors, store lock wait
- [ ] **Webhook mode** — long polling and the single-writer DB both pin `replicas: 1`; needed before a second replica, not before 1000 users
- [ ] **Per-provider rate limiter** — retry covers a 429 after the fact; a token bucket per provider would avoid earning one

### Cost
- [ ] **Token usage per run** — log input / cached / output tokens into `request_log` from rig's final response; until then every model-cost comparison is arithmetic on guesses
- [ ] **Cache-friendly prompt** — the per-user profile facts sit inside the system prompt and break the prefix cache per user; move them to the end
- [ ] **Provider config** — `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY` so a second provider is a config change (`MINIMAX_BASE_URL` exists; the model name does not)
- [ ] **GPT-5.6 Luna trial** — postponed 2026-09-05. Roughly 30% cheaper than MiniMax M3 on list price, but reasoning tokens may eat it, and Luna needs the Responses API for tools + reasoning. Try it on the tool-less side calls first, once usage logging exists
- [ ] **Search fan-out** — Kagi at up to 15 queries per run is the dominant cost, an order of magnitude above the model; measure how often the later queries add a result

- [ ] **Repair turn inside the flight desk** — a tool call written as prose in the nested run is now reported as a failure (`7356fa7`); one `REPAIR_NOTE` turn inside the nested run, as `run.rs` does for the main agent, would keep the research instead

### Hygiene
- [ ] **Duplicate dependency trees** — reqwest 0.12 + 0.13, rand 0.8/0.9/0.10, sha2 0.10/0.11; bumping reqwest to 0.13 (what rig uses) drops one TLS stack
- [ ] **`proc-macro-error2` future-incompat** — transitive; check for an updated upstream
- [ ] **Backup restore drill** — the restic repository has never been restored from; one rehearsal on a scratch node
- [ ] **Concurrency doc** — `docs/2026-08-08_225900-scout-100-concurrent-users.md` is in Russian while everything else is English, and most of it has shipped; rewrite as a status page or retire it
- [ ] **`target/` is 49 GB** locally — `cargo sweep` or a periodic clean

- [x] 2026-09-18 — **The printed plan opens on the days, and fits a page** (`4a8aa32`): the days of the trip are printed first, the same rows the page draws — a printed plan is carried, and the question it is opened on is what Thursday holds. `day_rows.json` holds the cases both suites read, so the Rust that prints them and the JavaScript that draws them cannot drift, the arrangement the connection check already uses. The document was also spending its pages on furniture: measured in a browser at A4 on a seven-item trip, 421mm before and 285mm after — 1.54 pages down to 1.04 with the day list added on top. Five fact tiles became one line; a card's place, state and tickets became one line instead of three; the title came down from 24pt; an alternative nobody chose is one line rather than a three-line block.
- [x] 2026-09-18 — **An item already on a trip can be corrected** (`d5f3dd9`): nothing could change an item once it existed, so a wrong time or a corrected branch meant remove and re-add — losing the tickets that came with the item and its link back to the confirmation it was read from, and renumbering the trip. Asked to fix something, the desk's only honest offer was a duplicate on the same day. `update_trip_item` takes only what changes; an empty string clears a place, a time or an end date, and a title cannot be emptied because the item is drawn by it. A flight goes to `update_trip_segment`, named in the model's words rather than the store's. The clock hangs off the item's own day, so moving the day moves the time with it; positions are recomputed; and an end date is checked against the date the item will have, not the one it had.
- [x] 2026-09-18 — **The trip reads as a row of days** (`d99c9d2`): the strip at the top drew flights and nothing else, so a trip with none had no overview at all, a hotel appeared nowhere on it, a free day was invisible, and a leg showed only its departure date — an overnight to Hong Kong read as a teleport. One row per day now, under the route that stays where it was; each thing on a day links to its card, a leg landing the next day sits on both rows pointing at one card, and a stay says its nights on the day it starts and marks the day it ends. A single empty day keeps its row, since "nothing on the 23rd" is an answer somebody wants; a run of them is counted, so an eSIM dated a week before departure cannot push the trip off the screen. Days are computed in UTC from the written strings: these are calendar days, not moments, and a summer-time jump would drop or repeat one. Rows stay rows on a phone.

- [x] 2026-09-17 — **A note on an itinerary item** (`47c348d`): asked for a Google Maps link on a lunch already on a trip, Scout could only offer a duplicate activity with the link in its title — `trip_items.notes` was storable only by `add_trip_item`, and nothing drew it. `note_trip_item` gives chat a way to write or clear a note on an item already there, `/chat/trips/item-note` gives the page one, and both check the item against what the caller drew, because positions are recomputed on every write and a link on the wrong item is quieter than the wrong item disappearing. - [x] 2026-09-17 — **A file that belongs to nobody** (`3f3f3fb`): an attachment is reached through the mail it came with, or once that mail is gone through the trip behind the item it joined — and deleting the item touched no files, so a swept mail plus a removed item left a row nobody could reach and neither sweep could find, its deletes being keyed on a mail id that no longer exists.
