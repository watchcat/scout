# One Way In — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One hop from the landing page to the chat for someone who has been here before, and one page for someone who has not.

**Architecture:** The public landing page learns one bit — whether a valid session cookie exists — by HMAC alone, with no database and no `Core`. It gains cache headers because a page that varies by cookie must not be stored by anything shared. Signing in lands on `/chat`, and `/sign-in` redirects a session it already has.

**Tech Stack:** Rust workspace (`scout-web`), `axum` 0.8, HMAC-signed session cookies.

---

## Read this first

**The cache headers are the load-bearing change, not the personalisation.**
`/` sends no cache directives at all today, which is safe only while every
visitor receives identical bytes. The moment it varies by cookie, a shared
cache with no instructions may store one visitor's page and serve it to
another. No account data leaks — the page holds no name, address or history,
and the session lives in the cookie rather than the markup — but the wrong
door is shown, and it reads as a session bug.

If you implement the personalisation and skip the headers, you have made
things worse than they were. Task 2 does both, in that order, and its test
asserts the headers.

**No database, and this is the point.** `session::verify` is an HMAC
comparison and an expiry check. The public router gets the session key and
nothing else — never a `Core`. `lib.rs` says why: *"giving it a `Core` it does
not use would be an invitation to query the database from the one path that
exists to avoid doing that."* If you find yourself needing `is_member` on this
page, stop: the design deliberately does not know, and `/chat` absorbs the
queued case with a redirect that already exists.

**Acceptance rule, as in the last three plans.** Changing `render`'s signature
forces mechanical edits to its callers.

> **No test's assertions or expected values change.** Only the argument passed
> to `render` changes, and only because its type changed.

struct Public {
    cache: AdmissionCache,

    /// a session is an HMAC comparison — no store, no `Core` — which is why
    /// this page can know who is reading it without becoming the database

    ///
    /// `None` is a deployment with no auth keys: no sessions can exist and
    /// no sign-in route does either, so the page must link to neither.

}

fn router(cache: AdmissionCache, auth: Option<AuthState>) -> Router {
    let session_key = auth.as_ref().map(|a| a.cfg.session_key.clone());

        // down for a reason the site does not have.

- [ ] **Step 4: Read the cookie and send the headers**

```rust
async fn index(State(public): State<Public>, headers: HeaderMap) -> impl IntoResponse {
    let visitor = match &public.session_key {
        // No keys, so no sessions and no sign-in route to link to.
        None => page::Visitor::NoAuth,
        Some(key) => {
            let session = headers
                .get(header::COOKIE)
                .and_then(|jar| jar.to_str().ok())
                .and_then(|jar| session::read_cookie(jar, session::COOKIE))
                .and_then(|value| session::verify(key, &value));
            match session {
                Some(_) => page::Visitor::SignedIn,
                None => page::Visitor::SignedOut,
            }
        }
    };
    (
        [
            // This page now differs by cookie. Without both of these a
            // shared cache may store one visitor's version and serve it to
            // another — the headers are the cost of personalising it, not
            // an optimisation.
            (header::CACHE_CONTROL, "private, no-store"),
            (header::VARY, "Cookie"),
        ],
        Html(page::render(&public.cache.get(), visitor)),
    )
}
```

Add whatever imports this needs (`HeaderMap`, `IntoResponse`) following the
file's existing `use` style.

## What this deliberately does not do

- **Show membership on `/`.** It would need `is_member`, and the database read
  the admission cache exists to avoid. A queued visitor is absorbed by
  `/chat`'s redirect instead.
- **Put an email field in the hero.** That would give the public router CSRF
  state and a `POST` handler, and the Telegram widget cannot appear on the
  public page without loading a third party's script onto it.
- **Touch the landing page's prose.** It never claims Scout is Telegram-only;
  only the call to action needed changing.
