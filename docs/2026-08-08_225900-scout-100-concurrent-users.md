# Scout: масштабирование до ~100 одновременных пользователей

> **Для Hermes:** это аналитический план; реализация пойдёт через
> `subagent-driven-development` если пользователь даст добро.

**Цель:** чтобы бот корректно (без деградации качества ответов, без
блокировок от внешних API, без DoS друг на друга) обслуживал порядка
100 пользователей, которые могут одновременно слать запросы.

**Архитектура сейчас (на 2026-08-08):** один tokio-процесс, один
`reqwest::Client`, общий `Store` поверх одного DuckDB `Connection`
под `Arc<Mutex<…>>`, in-memory `DashMap` для сессий, allowlist
через `ALLOWED_TELEGRAM_USER_IDS`.

---

## TL;DR — где упрётся и в каком порядке чинить

По убыванию риска:

1. **DuckDB — один `Connection` под `Mutex`.** Любой SELECT/INSERT
   сериализуется. При 100 пользователях, каждый из которых делает
   несколько записей за сессию (`record_purchase`, `remember_fact`,
   `request_log`, имя в `users`), плюс тяжёлый `usage_stats` для
   `/stat` — это первое реальное узкое место. *Не блокирующее* на
   одной операции (DuckDB быстрый), но *суммарно* оно задержит все
   ответы.
2. **Внешние API не шарят ни одного rate-limit.** Kagi, Perplexity,
   eBay, bol.com, Duffel, Ignav — все общие, лимиты у каждого свои.
   Один человек, который инициирует 20 запросов подряд, съедает
   бюджет и для остальных. Нужны per-user лимиты запросов и общий
   семафор на «дорогие» вызовы.
3. **LLM-агент — единственный MiniMax-ключ, один HTTP client rig-core.**
   `MAX_TURNS = 20` на запрос; при 100 одновременных это 2000 turns
   потенциально в полёте. MiniMax API умеет держать нагрузку, но
   бюджет в долларах закончится очень быстро. Нужны per-user
   лимиты на количество активных «run» и per-user очереди.
4. **Headless Chrome (`Renderer`) — штука дорогая.** Один процесс
   Chromium на 100 человек — ок, но если 10 человек одновременно
   пошлют запрос на Cloudflare-сайт, получим 1
5. 0 параллельных
   рендеров и всё встанет. Нужен семафор вокруг рендерера.
5. **In-memory `DashMap` сессий — вырастет до ~200 entries при 100
   пользователях** (чаты × пользователи). Это копейки по памяти,
   но нет вытеснения: пользователь, который пришёл однажды и больше
   не пишет, сидит в `chats` вечно (TTL 10 минут чистит только
   активные).
6. **`ALLOWED_TELEGRAM_USER_IDS`** — env-переменная с
   comma-separated id. На 100 человек это уже неудобно. Не блокер,
   но UX-боль.
7. **`ALLOWED_TELEGRAM_USER_IDS` не масштабируется по
   *стоимости* запроса:** сейчас бюджеты — на запрос, а не на
   пользователя. Один из 100 может потратить бюджет, выданный
   остальным 99, и они увидят отказы. Нужны per-user лимиты.

## 1. DuckDB: уйти от `Mutex<Connection>` к пулу

**Файл:** `src/store.rs` (сейчас `Arc<Mutex<Connection>>`).

**Симптом:** `lock().unwrap()` на каждой записи (`record_purchase`,
`log_request`, `upsert_user_name`, `set_next_due`, `remember_fact`,
`forget_fact`, `create_reminder`, `cancel_reminder`, `usage_stats_*`,
`flight_searches_*`, `broadcast_targets`, `display_names`).
Каждый блок — сериализованный `await` под мьютексом.

**Проблема:** DuckDB не рассчитан на сотни писателей; у duckdb-rs
один `Connection` — это один коннект, и даже чтения под записью
блокируются.

**Решение (три варианта по возрастанию инвазивности):**

**A. Connection-pool (минимум изменений).** Использовать
`duckdb::pool` если доступен, или r2d2-подобную обёртку. Каждый
`Store::method` берёт коннект из пула на время операции.
- Плюсы: минимальные изменения в вызывающем коде.
- Минусы: `duckdb-rs` исторически не имел хорошего пула; проверить
  актуальное состояние. Конкурентные записи всё равно сериализуются
  на уровне файла WAL.
- Стоит начать с него; многих пользователей устроит.

**B. Разделение read/write.** `Store` держит пул read-коннектов
для SELECT и отдельный write-коннект для INSERT/UPDATE. Чтения
идут параллельно, записи — через очередь.
- Плюсы: чтения (а их большинство в `bot.rs`) не блокируются
  друг другом.
- Минусы: write-очередь надо аккуратно сделать, чтобы не было
  starvation.

**C. SQLite или PostgreSQL.** Если вы готовы менять БД,
`rusqlite` с `bundled` + WAL даст реальную конкурентность из
коробки. Postgres ещё лучше, но добавляет сервис.
- Это уже изменение стека; обсудить отдельно.

**Что сделать прямо сейчас (Task 1):**

1. Снять метрики: добавить `tracing` spans вокруг каждого
   `store.*` вызова с временем блокировки.
2. Запустить нагрузочный тест (даже синтетический, через
   `delegate_task` + скрипт, шлющий сообщения через Telegram
   Test API если есть) — понять, сколько мс уходит под мьютексом
   на N одновременных пользователях.
3. По цифрам выбрать A/B/C.

## 2. Per-user rate limits на запросы

**Файлы:** новый `src/rate_limit.rs`, изменения в `src/bot.rs` и
`src/config.rs`.

**Зачем:** сейчас `SearchBudget` (`src/tools/budget.rs`,
`QUERIES_PER_REQUEST = 15`) и `FlightBudget`
(`BASE_FLIGHT_SEARCHES = 4`) — это per-request лимиты. Они
останавливают одну разогнанную сессию, но не одного разогнанного
пользователя, который шлёт сообщения каждые 5 секунд.

**Решение:**

**A. Окно запросов на пользователя.** Token bucket per user_id:
- N активных одновременных runs (например, 3 — пользователь
  может послать follow-up, пока первый ещё пишет).
- M сообщений в минуту (например, 10 — больше никто не пишет).
- Если превышено — короткое сообщение «подождите N секунд».

**B. Общий семафор на дорогие вызовы.** Глобальный
`tokio::Semaphore` (например, 20 permits) вокруг:
- `headless Chrome render` (это самое тяжёлое; у браузера и так
  своя очередь, но семафор даст fairness между пользователями).
- `search_flights` (Duffel/Ignav платные).
- `search_web` Kagi (Kagi биллит per query).

**Task 2:** добавить `rate_limit` модуль, покрыть тестами
поведение «10 сообщений в минуту от user X, 11-е отбито», и
проверить, что семафор не превращает редкий запрос в «никогда».

## 3. Конкурентные runs на одного пользователя

**Файл:** `src/bot.rs`, `src/agent.rs`.

**Симптом:** в `ChatSession` (в `DashMap`) сейчас одно поле
`history`. Если пользователь шлёт второе сообщение, пока первый
run ещё стримит ответ, его `history` уже мутируется —
классический data race на уровне логики (Rust-овый код это
ловит только если два tokio-task'а пишут одновременно, но
семантически — пользователь увидит «ответил на чужой вопрос»).

**Решение:**

**A. Один активный run на `(chat_id, user_id)`.** `JoinHandle`
текущего run хранится в `ChatSession`. Новое сообщение во время
активного run либо:
- кладётся в очередь и обрабатывается после завершения текущего
  (поведение как сейчас у большинства ассистентов), либо
- отбивается с «уже отвечаю, допишите позже».

**B. Per-user очередь длиной 1.** Если пришло новое сообщение
пока run активен — оно заменяет предыдущее (или копится в
`pending: VecDeque<Message>` с лимитом). Это ленивый UX:
пользователь дописывает, не ждёт.

**Task 3:** выбрать A или B (вероятно B), реализовать в
`ChatSession`, написать тест на гонку.

## 4. Allowlist на 100 человек

**Файл:** `src/config.rs`, новый `src/access.rs`.

**Симптом:** `ALLOWED_TELEGRAM_USER_IDS=111,222,333,...,999` —
это CSV в env, и любой апдейт = перезапуск + диф в git. При 100
людях это больно.

**Решение (выбрать одно):**

**A. Таблица в DuckDB** (`allowed_users(user_id BIGINT PK,
added_at TIMESTAMP, notes TEXT)`), команда `/allow <id>` для
админа. Тот же `ALLOWED_TELEGRAM_USER_IDS` остаётся как bootstrap
(первый запуск читает env, добавляет в таблицу, дальше env
игнорируется).
- Плюсы: админ управляет через бота, история видна.
- Минусы: первый запуск всё ещё требует env.

**B. Файл `allowed.txt`** (один id на строку), mounted volume.
Перечитывается каждые 60 секунд (cheap reload).
- Плюсы: просто, прозрачно, можно gitignore с локальным override.
- Минусы: нет аудита.

**Task 4:** обсудить с пользователем предпочтение. Я бы выбрал A,
потому что бот сам подсказывает команды, и `/allow` логично
существует.

## 5. Headless Chrome: семафор + лимит на одного пользователя

**Файл:** `src/tools/browser.rs`, `src/tools/fetch.rs`.

**Зачем:** Chromium — single-process по умолчанию (или
multi-process, но всё равно тяжёлый). Если 20 пользователей
одновременно посылают запрос на Cloudflare-сайт, бот откроет 20
вкладок и либо убьёт память, либо встанет в очередь к
единственному render pool.

**Решение:**

- `tokio::Semaphore::new_acquire(4)` (или по числу CPU / 2)
  вокруг `Renderer::open`.
- Per-user лимит: «не больше 1 активного render за 30 секунд».
  Если пользователь только что получил Cloudflare-fallback, не
  делать ему ещё один render в течение 30 секунд.

## 6. Бюджеты per user, а не per request

**Файл:** `src/tools/budget.rs`, новый `src/user_budget.rs`.

**Симптом:** `SearchBudget` создаётся в `build_agent` per request
(`agent.rs`). Он ограничивает один run, но не cumulative spend
пользователя.

**Решение:**

Per-user счётчик:
- Kagi queries: ≤ 100 в день на пользователя (настраивается).
- Flight searches: ≤ 30 в день.
- LLM turns: cumulative cap per user per day.

При превышении — сообщение «это ваш N-й запрос сегодня, лимит
X; подождите завтра» (а не отказ без объяснения).

Это даёт предсказуемую стоимость и защищает от
«один пользователь сжёг месячный бюджет MiniMax».

## 7. `/stat` под нагрузкой

**Файл:** `src/bot.rs` (`Command::Stat`).

**Симптом:** `/stat` уже сейчас использует `spawn_blocking` для
SQL — это хорошо. Но запросы `usage_stats_all` сканируют всю
таблицу `request_log`. При 100 активных пользователях, каждый из
которых делает 30 запросов в день = 3000 строк в день, через
месяц = 90 000 строк, через год = миллион. Полный скан в DuckDB
под мьютексом — секунды.

**Решение:**

- Индексы: `CREATE INDEX IF NOT EXISTS idx_request_log_user_time
  ON request_log(user_id, created_at)`.
- Materialized daily rollup: отдельная таблица
  `usage_daily(user_id, day, count)`, обновляемая триггером или
  фоновым таском раз в час. `/stat` читает из rollup.
- Кеш `/stat` per (admin, days) на 30 секунд, чтобы 10 админов
  не генерировали 10 одинаковых запросов.

## Что **не** нужно делать для 100 человек

- **Шардирование бота по процессам / k8s.** 100 человек на
  современном железе в один процесс с Tokio вполне тянутся, если
  убрать мьютекс DuckDB и добавить rate limits.
- **Переписывать с teloxide на что-то ещё.** Teloxide нормально
  держит нагрузку; проблема не в нём.
- **Переезжать с MiniMax.** Если есть риск по лимитам MiniMax —
  обсудить с пользователем отдельно, но это не блокер для
  технической готовности.

## Открытые вопросы для пользователя

1. **Бюджет:** на 100 пользователей умножение текущих расходов на
   MiniMax + Kagi + Duffel — это нормально, или есть потолок?
   (Нужно, чтобы выставить лимиты в Task 6.)
2. **Allowlist:** A (таблица в DuckDB + `/allow`) или B (файл)?
3. **Per-user queue:** новое сообщение во время активного run —
   ставить в очередь или отбивать «подождите»?
4. **Целевая нагрузка:** «100 одновременно пишущих» — это
   пиковая или постоянная? Сколько запросов в день на человека
   ожидается?
5. **Что важнее: latency или throughput?** Если latency — это
   заставляет смотреть на Task 1 (мьютекс) первым. Если
   throughput — Task 3 (rate limits).

Как только эти пять ответов получены, Task 1 (метрики) можно
запускать, остальное пойдёт по плану сверху.
